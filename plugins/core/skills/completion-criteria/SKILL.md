# Completion Criteria

実装の前に「何ができたら終わりか」を3〜5行で固定する。労力の9割は実装前にある。ここが曖昧なまま書き始めると、戻ってきたものを裁けない。

## 手順
1. 依頼を読み、完了条件を3〜5行で書く。各行は次の形にする
   - 観測できる結果で書く（「〜できる」「〜のとき〜になる」）。「〜を実装する」は条件ではない
   - 機械的に合否が出る確認方法を添える（テスト名、コマンド、スクリーンショット比較）
   - 1行に1条件。「および」「かつ」で2つを束ねない
2. 境界と失敗系を少なくとも1行入れる（空入力、権限なし、通信失敗、二重実行など）
3. 変えないことを1行入れる（既存テストが全て通る、既存データの形式を変えない、など）
4. ユーザーに提示し、合意を取ってから実装やテスト作成に進む。自動実行中で確認できない場合は、条件を書いた上で「この条件で進める」と明示して進む
5. 合意した完了条件は、テスト作成者（Codex）とレビュアー（fresh-reviewer）にそのまま渡す

## 書き方の例

依頼: 「スマートリストの件数がずれるのを直して」

完了条件:
- 空のスマートリスト応答を受け取ったとき、サイドバーの件数が 0 になる（tasks.spec.ts の該当テストが GREEN）
- 別のスマートリストを選択した後に古い応答が届いても、表示と件数が上書きされない（連番ガードのテストが GREEN）
- 応答が例外で終わったときも loading が false に戻る（失敗系テストが GREEN）
- 既存の web テスト、型チェック、lint が全て通る（npm run test:run / type-check / lint）

## やらないこと
- 条件を6行以上に増やす。増えるなら作業を分割する
- 実装方法を条件に書く。条件は結果、方法は計画書に書く
