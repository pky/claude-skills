# PR を作った後の流れ

## 決まり

- Herdr の中（HERDR_ENV=1）で PR を作った会話は、自分では見張らない。下の「Herdr の中での渡し方」で新しいペインの Claude に見張りを渡し、PR の URL と渡し先のペインを報告して終える。PR を作るまでに積み上がった文脈を、見張りの往復ごとに読み直さないため。引継ぎメモで見張り役として起動された会話は、渡さずに自分で見張る。Herdr の外では、PR を作った会話がそのまま見張る
- PR を作ったら、下の「変化を待つ見張り」で CI（GitHub Actions があるリポジトリだけ）と Codex の自動レビューの未解決スレッドを見張り、変化を知らせる行が届くたびに「毎回の確認の手順」を回す。指摘は既存の流れ（修正は Codex、差分レビューは fresh-reviewer）で直して、コミットと push まで進める。指摘が妥当でないときは直さず、そのスレッドに直さない理由を返信する。スレッドの resolve はレビュアーに任せる
- Codex の自動レビューは PR を開いたときにしか走らない。PR を開いた後に push したら、PR に `@codex review` とコメントして最新のコミットを再レビューさせる。Codex のサマリーコメントに書かれたコミットが、PR の最新のコミットと一致するまでは、レビュー済みとみなさない
- レビュー指摘を直す push は、1つの PR で3ラウンドまで: 3回直しても新しい指摘が続くなら、それ以上は直さない。残った指摘を一覧にし、作り方そのものを見直すべきかの判断を添えてユーザーに報告する。報告のあとも見張りは続けるが、新しい指摘は直さずに一覧へ足す。指摘を直すときは、指摘された行だけでなく同じ種類の間違いをほかの箇所でも探し、1回の push でまとめて直す
- マージできる状態の条件: CI があれば green、Codex のレビューが最新のコミットまで済んでいる、未解決スレッドがすべて「直した」か「理由を返信済みで、その後に新しい指摘がない」。満たしたら1回だけ報告し、理由を返信して直さなかった指摘の一覧を添える。報告には次の3つも書く。この PR で何が変わるかを2〜3行で。人が理解してからマージすべき箇所を file:line 付きで最大3つ（データを壊しうる変更、権限や秘密情報、CI や設定、あとで真似される設計の決め方。当たらなければ「なし」と書く）。テストとレビューが見ていない部分（実機での動作、ネットワークの失敗、既存データの移行など）。報告したら見張りの Monitor を TaskStop で止め、起動し直さない。マージまでは監視しない。PR がマージされたとユーザーから聞いたら、worktrunk:worktree-flow スキルの手順で worktree とローカルブランチを消す。片付けの報告には、その PR の変更範囲に合わせたデプロイコマンド（例: web だけなら Hosting、Functions やルールも変えたらその分）を、ビルドなどの前準備も含めて貼れる形で添える。デプロイ自体は実行しない

## Herdr の中での渡し方

1. 引継ぎメモを `<TMPDIR>/babysit-handoff/<リポジトリ名>-<PR 番号>.md` に書く。`<TMPDIR>` は sandbox の中で実行した `printenv TMPDIR` の出力で、絶対パスにしてから書く（sandbox の外では別の場所が返り、見張り役が読めない）。会話ごとの scratchpad には置かない（見張り役は別の会話なので、元の会話が終わると読めなくなる恐れがある）。見張り役は今の会話を読めないので、次をすべて書く
   - PR の URL と番号、リポジトリ、ブランチ、基点ブランチ、worktree の絶対パス
   - 元の会話のペイン（`printenv HERDR_PANE_ID` の出力）
   - 仕様と完了条件の要点、その正本の場所（spec、台帳ファイル）
   - リポジトリの指示ファイルにある検証コマンドと、PR を作るまでに通した検証
   - 指摘を直すときの注意（触ってよい範囲、テストは変更禁止、やらないこと）と、まだ残っている事項
   - 最初の行に「この会話は PR #<番号> の見張り役。pr-auto:babysit の決まりで見張り、別の会話へ渡さない」
   - 2行目に「最初に `cd <worktree の絶対パス>` だけを1回実行してから作業する」
2. ペインの分割先は herdr:codex-in-herdr スキルの決め方に従い、`--cwd <メインの作業ツリー>`（`git worktree list` の先頭の行のパス）を付けて割る。worktree では割らない（Claude Code は、起動した場所と cd した今の場所に `.claude/.cc-writes` を作り直すので、worktree で起動すると、片付けたあとに空のフォルダが残る）。返る pane_id を控える
3. `herdr agent start babysit-<リポジトリ名>-<PR 番号> --kind claude --pane <pane_id>` で Claude を起動する。agent 名は動いている agent の中で一意でなければならないので、リポジトリ名を入れる（32文字を超えるならリポジトリ名を切り詰める）。準備ができるまで待って返る
4. `herdr agent prompt <pane_id> "Read <メモの絶対パス> and follow it. Run pr-auto:babysit for PR #<番号>." --wait --until working --timeout 60000` で渡す。3か4が失敗したら、`herdr agent read <pane_id>` で画面を読んで原因を報告に書き、渡すのをやめて元の会話が自分で見張る
5. 報告の前に、元の会話はメインの作業ツリーへ `cd` だけを1回実行し、worktree から出る（出ないと、片付けたあとに元の会話が空のフォルダを作り直す）。報告には、PR の URL、渡し先の pane_id、メモの絶対パスを書く。ペインは片付けが終わるまで閉じない
6. 見張り役は、マージできる状態の報告を書いたら、メモにある元の会話のペインへ `herdr agent prompt <元の会話のペイン> "PR #<番号> is ready to merge."` で知らせる。利用者は元の会話を見ているので、見張り役のペインに書くだけでは伝わらない。知らせを受けた元の会話は、利用者に「PR #<番号> はマージできます。今まで通りメインの作業ツリーでマージしてください」と伝える。見張り役が「変化を待つ見張り」の error で見張りを止めたときも、同じように `herdr agent prompt <元の会話のペイン> "PR #<番号> babysit stopped: <error 行>"` で知らせ、元の会話は error 行と見張りが止まったことを利用者に伝える
7. PR がマージされたあとの片付けは見張り役だけが行う。元の会話が利用者からマージを聞いたら、自分では片付けず、`herdr agent prompt <pane_id> "PR #<番号> was merged. Clean up per pr-auto:babysit."` で見張り役に伝える。見張り役は、片付けの前に自分の見張りの Monitor を TaskStop で止める（3ラウンドを超えたあとは見張りが続いているため）。元の会話は、伝えたあと `herdr agent wait <pane_id> --timeout 600000` で片付けの終わりを待ち、`herdr agent read <pane_id>` で片付けの報告を読んで利用者に伝え、`herdr pane close <pane_id>` で見張り役のペインを閉じる（終わった見張り役のペインを残さないため）

## 変化を待つ見張り

決まった間隔でモデルを起こさず、同じディレクトリの scripts/wait-for-change に PR の状態を見張らせ、変わったときだけ起きる。変化がない間は、確認のたびに文脈を読み直さない。

- 前提: settings.json の sandbox 直下に `"enableWeakerNetworkIsolation": true` がある。無いとスクリプトの中の gh が sandbox の中で証明書の確認に失敗する（x509 OSStatus -26276）。無ければ見張りを始めず、足すかを利用者に聞く
- Monitor で次を起動する。timeout_ms は 1800000、allowed_domains は `["api.github.com"]`。`<owner>/<repo>` は `gh repo view --json owner,name` の値、`<TMPDIR>` は sandbox の中で実行した `printenv TMPDIR` の絶対パス

```bash
<skill_dir>/scripts/wait-for-change --repo <owner>/<repo> --pr <number> --state <TMPDIR>/babysit-state/<リポジトリ名>-<PR 番号>.json
```

- スクリプトは保存した前回の状態（head の SHA、CI の各チェック、未解決スレッドと最終コメント、レビューとコメントの件数）と60秒ごとに比べ、変わったら `changed: <項目>` を1行出して終わる。状態ファイルが無い初回は `initial: <パス>` を出してすぐ終わる。gh が3回続けて失敗したら `error: <要点>` を出して終わる
- 1行届いたら（`initial:` を含む）「毎回の確認の手順」を1回回し、終わったら同じコマンドで起動し直す。直すものが無いとき、CI が実行中のとき、3ラウンドを超えて一覧に足すだけのときも起動し直す。起動し直さないのは、マージできる状態を報告したとき、片付けの前に止めたとき、下の error で止めたときだけ。`error:` が届いたら行の中のエラーで原因を確かめる。一時的な通信の失敗なら起動し直す。認証切れ、PR やリポジトリが見つからない、状態ファイルを読み書きできない、など自分では直せない原因のとき、または起動し直して続けて2回 `error:` が届いたときは、起動し直さずに止め、error 行と確かめたことを利用者に報告する。Monitor の期限切れ（30分）の通知が来たときも起動し直す。状態ファイルは終わったときにしか書き換わらないので、起動し直すまでの間の変化も次の起動ですぐ届く

## 毎回の確認の手順

1. PR の番号、ブランチ、基点ブランチを確かめる
2. PR が draft でないことと、マージできるか、CI、レビューの判定、コメント、スレッドを見る
3. 新しいコメントと未解決スレッドを読む。bot のサマリーは参考にするが、指摘はコードと照らして確かめる
4. 本物の指摘は、決まりのとおり直してテストやビルドを通し、push してから見張りを起動し直す
5. bot の指摘が古いコードに対するものなら、スレッドが outdated か、最新のコミットで直っているかを確かめる
6. 最後の報告の前に、PR の状態、未解決スレッド、最近のコメント、手元の `git status` をもう一度まとめて見る
7. 報告には、最新のコミットの SHA、CI の名前と結果、未解決スレッドの数、走らせたテスト、手を付けずに残した未コミットのファイルを書く

## gh のコマンド

PR の大まかな状態:

```bash
gh pr view <number> --json number,state,isDraft,mergeable,mergeStateStatus,reviewDecision,headRefOid,statusCheckRollup,url
```

owner と repo の名前（GraphQL に渡す値。出力を見て、次のコマンドにそのまま書く）:

```bash
gh repo view --json owner,name
```

未解決スレッドの一覧。`<owner>` と `<repo>` には上の値を、`<skill_dir>` にはこのスキルのディレクトリの絶対パスを書く。クエリは同じディレクトリの review-threads.graphql にある。クエリをコマンド行に直接書くと許可の確認で拒否されるので、必ずファイルで渡す。整形は jq を使わず、返ってきた JSON の `isResolved` が false のものを読む:

```bash
gh api graphql -F query=@<skill_dir>/review-threads.graphql -f owner=<owner> -f repo=<repo> -F number=<number>
```

`hasNextPage` が true のときは、同じコマンドに `-f cursor=<endCursor の値>` を足して、次のページを1回ずつ取る。シェルの変数やループで回さない。

PR の本文とコメントは、scratchpad のファイルに書いて `--body-file` で渡す。スレッドへの返信は gh api で送るので、本文ファイルを `-F body=@<ファイル>` で渡す（gh api には `--body-file` が無い）。gh のコマンド行にバッククォートを入れると、sandbox の除外設定 `gh *` が効かずに sandbox の中で動き、GitHub への通信が拒否される。
