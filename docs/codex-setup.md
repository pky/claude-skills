# Codex単独統括環境の導入手順

仕事MacのCodexへ、この文書のURLと次の依頼文を渡してください。

> この文書に従い、既存の仕事向け設定を保全してCodex単独統括環境を設定し、最後に検証してください。認証情報を別Macからコピーせず、必要な指示と設定だけを統合し、結果と未確認事項を報告してください。

## 1. 導入状況と認証を確認する

会社・組織の管理設定と許可範囲を優先します。まず次を確認し、導入済みのCodex・Herdrは再インストールしません。

```bash
codex --version
herdr --version
codex plugin marketplace add --help
codex plugin add --help
```

未導入のものだけ、会社が認める公式経路で導入します。[Codex CLI](https://developers.openai.com/codex/cli)と[Herdr](https://herdr.dev/tui/docs/install/)の公式手順を参照してください。HerdrのCLIとGUIアプリは別なので、GUIで管理する場合はアプリの有無も確認します。必要なCLI機能がない場合は、既存の導入方式を確認して更新し、上記コマンドを再確認します。

```bash
codex login status
```

未認証なら `codex login` で仕事用アカウントにログインします。認証情報、履歴、DB、キャッシュ、SSH鍵、APIキー、個人のMCP設定を別Macからコピーしません。GitHubやMCPの認証は必要なものだけ仕事Macで接続します。[認証の公式説明](https://learn.chatgpt.com/docs/auth)も参照してください。

## 2. 既存設定を保全する

既存の `CODEX_HOME` は変更しません。未指定なら `~/.codex`、指定済みならそのディレクトリを設定先として使います。以降の `AGENTS.md` と `config.toml` は、この設定先のファイルを指します。

```bash
ls -ld "${CODEX_HOME:-$HOME/.codex}/AGENTS.md" "${CODEX_HOME:-$HOME/.codex}/config.toml"
```

ファイルがなければ未作成として扱います。既存ファイルがある場合は、symlinkとリンク先を確認し、変更前の内容とリンク情報を仕事Mac内の非公開領域へ退避します。元の有無・退避先・変更箇所も非公開で記録してください。設定内容や秘密値をチャットやGitへ貼らないでください。

既存の仕事・組織・リポジトリ向け指示、モデルprovider、MCP、権限・承認設定を保ち、必要な章とキーだけを差分で統合します。ファイル全体を無条件に上書きせず、組織の制約や既存のより強い制約を緩めません。

## 3. GitHubからプラグインを導入する

現在の検証済み公開ブランチは `feature/codex-marketplace` です。Codex版はmainに未反映のため、今は `--ref main` を指定しません。mainへの反映を確認した後に、この文書と登録先の参照refを `main` に変更します。

導入前に、CLIのヘルプと現在の登録状態から同名marketplaceのsource・ref・有効プラグインを確認し、非公開で記録します。同じsource・refと導入済みのプラグインは重複導入しません。同名sourceが異なる場合だけ、既存設定と旧sourceへの復旧方法を確認・退避した上で、対象の登録を外して再登録します。

```bash
codex plugin marketplace remove pky-codex-skills
```

上のremoveはsourceの差し替えが必要な場合だけ実行します。新規登録・未導入分には、次を順に実行します。他のmarketplaceやプラグインは保持します。

```bash
codex plugin marketplace add pky/claude-skills --ref feature/codex-marketplace
codex plugin add core@pky-codex-skills
codex plugin add pr-auto@pky-codex-skills
codex plugin add worktrunk@pky-codex-skills
codex plugin add herdr@pky-codex-skills
codex plugin list --marketplace pky-codex-skills --available --json
```

core・pr-auto・worktrunk・herdrの4件が利用可能で有効になっていることを確認します。登録済みsourceが同じでもrefが異なる場合は、その差とCLIが提供する変更方法を確認し、既存プラグインを保全して指定refに合わせます。導入に失敗した場合は今回の変更だけを戻し、旧source・refと既存プラグインの復旧を確認します。

iOS実機確認は任意です。既存の `ios-device-check` があれば二重導入しません。必要かつ未導入の場合だけ `codex plugin add ios@pky-codex-skills` を実行します。実機操作にはXcode・WDA・mobile-mcpなどが別途必要です。Worktrunk本体や `gh` も必要時に許可された方法で用意し、既存の導入を保持します。

参照: [marketplaceのCLI登録](https://developers.openai.com/plugins/build/plugins#add-a-marketplace-from-the-cli)。

## 4. AGENTS.mdに統括ルールを統合する

通常は `~/.codex/AGENTS.md` に、以下のルールを統合します。`CODEX_HOME` が指定済みならその設定先を使います。既存ルールとの重複や古い役割指定を確認し、必要な箇所だけ差分更新します。この文書にあるルールを使えるため、別の個人用指示ファイルを取り寄せる必要はありません。

### 言語とコミット

- 回答・技術説明・コードコメントは日本語で書く。
- コミットメッセージは日本語1行、50文字以内。Co-Authored-Byを追加せず、authorとemailはリポジトリの既存Git設定を使い、変更しない。

### 統括と作業者

- 通常の `codex` 起動では統括として依頼を待つ。起動だけで仕事を始めない。依頼後は要件・設計・完了条件・作業先・委譲・検証・レビュー・最終報告を管理する。
- 明示された作業者指定、またはClaude・親Codexからの具体的な引継ぎがある場合は、役割ラベルがなくても作業者を優先する。指定範囲と親の設計・完了条件に従い、変更が必要なら親へ返す。
- 引用中の「Claude」、環境変数、親プロセス、ペイン位置で役割を推測しない。役割不明なら許可範囲の調査だけを進め、委譲や設計変更の前に親へ確認する。
- 子セッションには「役割: 作業者」と担当・範囲・作業先・ブランチ・基点・要件・完了条件・検証方法・禁止操作を渡す。作業者は明示許可なく再委譲しない。
- 既に許可された作業に重複の承認待ちを追加しない。範囲の変更や新たに必要な判断・承認だけを確認する。

### モデル分担

| 担当 | 初期値 |
|---|---|
| 統括・通常設計 | Sol（`gpt-6.1-sol`）、high |
| 独立したテスト作成 | Sol（`gpt-6.1-sol`）、high |
| 実装 | 別セッションのSol（`gpt-6.1-sol`）、mediumまたはhigh |
| 通常レビュー | 独立したSol（`gpt-6.1-sol`）、high |
| 高難度設計・重大変更の追加レビュー | Astra（`gpt-6-astra`）、high |
| 誤字・表示文言・コメント修正、画面確認 | Terra（`gpt-6.1-terra`）、lowまたはmedium |
| 対象の明確な検索・列挙 | Luna（`gpt-6-luna`）、high |

この表は運用上の初期値です。仕事用アカウントと既存providerで利用可能なモデル・権限、個別指定を優先します。未対応モデルを利用可能と扱わず、許可内の代替か制約を報告します。複数領域の原因調査はSolを使い、APIフィールド名や保存キーの変更を軽微な文字修正として扱いません。Astraの追加レビューは必要時だけ使い、常駐させません。

### 品質と作業分離

- テスト作成・実装・レビューはそれぞれ別の新規セッションにする。会話履歴を丸ごと継承せず、各担当に同じ要件・仕様・公開インターフェース・完了条件と必要な資料を渡す。
- テスト担当は仕様から期待値を決め、本体を実装しない。実装担当はテストを変更しない。テスト修正が必要なら、親が仕様と照合してテスト担当へ戻し、修正後に関連検証をやり直す。
- 不具合修正では可能なら修正前の再現テストが想定した原因で失敗することを確認する。再現できなければ理由と未検証範囲を示す。
- レビューは具体的な失敗シナリオを示し、仕様からの逸脱、境界条件、失敗系、テスト値への決め打ち、検証不足を確認する。
- テスト・lint・型チェック等の失敗、テストを変更して合格させた状態、完了条件の不足、必要な機械検証の未実施を完了扱いしない。実行コマンド・結果・未確認事項を報告する。軽微な文言変更では不要なテストを増やさず、適切な機械検証を選ぶ。
- 同じworktreeの編集者は1体とする。指定先のGitルート・ブランチ・HEADを引継ぎと照合し、指定先と許可範囲を厳守する。環境を変更するテストと実装は並行させない。
- 作業分離が必要な場合は、導入済みの `worktrunk:worktree-flow` に従い、既存作業を保全する。既存のROADMAP・進捗資料を確認し、非公開の計画や引継ぎはGit管理外に置く。

### Herdr操作と安全境界

- Herdrで委譲する前に、インストール済みの `herdr:codex-in-herdr` の実際の `SKILL.md` を利用可能なスキル一覧から確認して読み、その手順と現行CLIに従う。親より権限を広げず、組織の権限・承認設定を緩めない。
- 自分で作成した子ペインは、担当の終了と結果・差分・検証・引継ぎを確認し、必要な内容を非公開で記録する。不要になったら、直前にID・担当・停止状態を再確認して自動で閉じる。
- 他者が作成したペイン、working・blocked・承認待ち・結果未読・未完了の担当があるペインは閉じない。
- `git push` は通常・force・force-with-leaseを含め、すべて実行禁止。pushは常にユーザーが手動で行う。コミット・開発続行・公開の依頼をpush許可と解釈しない。
- 自動merge、worktree・ブランチの自動削除は禁止する。削除は対象を明示したユーザーの依頼がある場合だけ扱う。完了後もレビュー可能なブランチとworktreeを残す。
- 秘密情報を出力しない。外部投稿や本番操作は明示された依頼の範囲だけで行う。

## 5. config.tomlの必要なキーだけを設定する

仕事用アカウントと既存providerで利用可能な場合に、トップレベルの次の2キーを設定します。既存のTOMLテーブル内へ誤って追加せず、既存キーがあればその箇所を差分更新します。

```toml
model = "gpt-6.1-sol"
model_reasoning_effort = "high"
```

利用できない場合は既存の利用可能なモデルを保持し、代替と制約を報告します。`config.toml` 全体を置き換えず、既存のprovider・MCP・権限・承認設定と組織の制約を保持します。`CODEX_HOME` も変更しません。[設定ファイルの公式説明](https://learn.chatgpt.com/docs/config-file/config-basic)を参照してください。

## 6. 新しいセッションで検証する

Herdrの管理ペインで新しい `codex` を起動します。Herdrの環境変数を偽装せず、実際の管理ペインを使います。まず読み取りだけで次を確認してください。

- core・pr-auto・worktrunk・herdrの4プラグインが有効で、各スキルを参照できる。
- 通常起動は統括として依頼を待ち、Claude・親Codexの具体的引継ぎがあれば役割ラベルなしでも作業者になる。
- 統括がテスト・実装・レビューの新規セッション分離、実装担当のテスト変更禁止、指定worktreeの厳守を理解している。
- 自作ペインの終了・結果確認・非公開記録・停止状態確認後の片付けと、他者・作業中・blocked・未読・未完了ペインの保全を理解している。
- 既存の仕事向け指示、provider、MCP、権限・承認設定が保持され、`git push` を実行しない。

読み取り確認だけでは、委譲や片付けの実動作まで検証済みとはしません。必要な場合だけ許可範囲内のサンプルで分離・機械検証・自作ペインの片付けを試し、実行コマンドと結果を記録します。本番や業務リポジトリへの試験書込みはしません。

最後に、変更箇所、利用モデル、4プラグインの状態、実施した検証と結果、未確認事項を報告します。未検証や失敗を完了扱いせず、設定導入の確認と実動作の確認を区別してください。

問題があれば仕事Mac内の退避データと比較し、今回変更した章・キー・登録だけを差分で戻します。古い全体コピーで後から追加された設定を消さず、既存プラグインや認証を一括削除しません。
