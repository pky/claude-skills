# 実装前の完了条件

Codex統括が、依頼と既存仕様から「何ができたら終わりか」を3〜5行で定める。作業者は引継ぎ済みの条件に従い、独断で再定義しない。不明点や条件の変更が必要なら親へ返す。

## 条件の書き方

- 1行に1つの観測可能な結果を書く。「〜を実装する」など実装方法は条件にしない。
- 各行に機械的な合否が出る検証方法を添える。テスト名、コマンド、画像比較など、作業に合う方法を使う。
- 空入力、権限なし、通信失敗、二重実行など、関係する境界・失敗系を少なくとも1行含める。
- 既存のデータ形式や既存テストなど、変えない仕様を1行含める。
- 6行以上になる場合は、条件を詰め込まず作業単位を分ける。

既に許可された具体的な作業は条件を提示して進め、重複した承認待ちを追加しない。新たな範囲、判断に必要な曖昧な仕様、承認が必要な操作があるときだけ確認する。必要な回答を待つ間は、それに依存しない調査を進める。

条件はテスト担当・実装担当・独立したレビュー担当へ同じ内容で渡す。テスト作成・実装・レビューは別の新規セッションとし、会話履歴を丸ごと継承しない。担当の起動と調整は統括が行う。最終結果を条件と照合し、検証できなかった条件は未検証として報告する。

## 例

依頼: 「一覧の件数がずれる問題を直して」

- 空の応答で表示件数が0になる（空応答のテストが成功）。
- 選択変更後に古い応答が届いても現在の表示が上書きされない（応答順序のテストが成功）。
- 通信失敗時も読み込み中の表示が解除される（失敗系のテストが成功）。
- 既存の件数集計仕様を維持する（既存テスト・型チェック・lintが成功）。
